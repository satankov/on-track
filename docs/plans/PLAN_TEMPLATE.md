# Change implementation plan

## Goal

State the observable outcome.

## Context and reusable precedent

Link relevant code, tests, ADRs, documentation, packages, and maintained open-source implementations.

## Acceptance criteria

List testable user or caller guarantees, including error, persistence, accessibility, and recovery behavior where relevant.

## Non-goals

State what this change intentionally excludes.

## Proposed design

Describe the smallest coherent design and affected boundaries.

## Data and migration impact

Describe schema, migration, transaction, backup, compatibility, and rollback concerns.

## Phases

1. Define one small, independently verifiable phase with its expected evidence.

## Test plan

Map each acceptance criterion to unit, integration, component, or E2E evidence.

## Risks and mitigations

List plausible failure modes and recovery paths.

## Open decisions

List only choices that genuinely block or materially alter implementation.

## Approval request

Ask the user to approve a named phase or request specific plan revisions. Do not begin implementation until approval is explicit.

## Completion evidence

Record RED/GREEN evidence, verification commands, results, and remaining risk. Do not store secrets or private context.
