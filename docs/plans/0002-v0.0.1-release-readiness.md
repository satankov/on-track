# v0.0.1 release-readiness implementation plan

## Goal

Prepare On Track for its first public source release as version `0.0.1`: apply
a public source license, provide a one-command first run, keep user data outside
the repository, and establish repeatable development, review, CI, security, and
tag-gated GitHub release workflows.

## Context and reusable precedent

The first project-chat slice and its verification evidence are recorded in
[plan 0001](0001-first-project-chat-slice.md). The runtime and persistence
boundaries are described in [ADR-0001](../adr/0001-localhost-typescript-sqlite.md)
and [ADR-0002](../adr/0002-defer-at-rest-encryption.md).

The repository already has a pinned npm lockfile and an aggregate `npm run
verify` gate. GitHub's supported Node workflow pattern uses `npm ci` with
`actions/setup-node`; GitHub release workflows can use the runner-provided `gh`
CLI and a least-privilege `contents: write` token. GitHub dependency review,
CodeQL, Dependabot, protected branches, and immutable releases provide maintained
building blocks instead of project-specific release infrastructure.

## Acceptance criteria

1. The project has a clearly identified public source license and public docs
   identify version `0.0.1` as an alpha release.
2. From a fresh source checkout with Node.js 24 and npm installed, `npm run
quickstart` installs locked dependencies, builds, migrates a local database,
   and starts the app at `http://127.0.0.1:4173`; `Ctrl+C` stops it.
3. Subsequent starts use `npm start`; development uses `npm run dev`.
4. The default database is created only in the operating-system application data
   directory, not the source tree. Database, journal, backup, export, environment,
   IDE, dependency, build, coverage, and browser-test artifacts are ignored.
5. A release check fails when the package and lockfile versions differ, the tag
   does not equal `v<package version>`, required public files are absent, or any
   SQLite/database file is tracked by Git.
6. Pull requests and pushes to `main` run build, typecheck, lint, format,
   coverage, migration, E2E, and dependency-security gates on Node.js 24.
7. Native dependency installation and the non-browser test suite run on Linux,
   macOS, and Windows.
8. Pull requests receive dependency review; JavaScript/TypeScript receives CodeQL
   analysis; npm and GitHub Actions dependencies receive weekly Dependabot checks.
9. A `v*.*.*` tag creates a GitHub Release only after release validation and the
   complete verification suite pass and only when the tagged commit is on
   protected `main`. Workflow actions are pinned to full commit SHAs and workflow
   permissions are least-privilege.
10. Contributor, security, and release instructions explain the repeatable
    dev -> test -> review -> release process, including repository settings that
    cannot be expressed safely in files.
11. No commit, tag, push, repository setting, or GitHub release is created by this
    implementation task.

## Non-goals

- Native `.dmg`, `.exe`, AppImage, package-manager, Docker, or mobile installers.
- Publishing the private application package to npm.
- Application-level encryption, backup/restore UI, or an NDA-safe claim.
- Creating the GitHub repository, changing remote settings, or publishing v0.0.1.
- Automatic semantic version selection or changelog generation.

## Proposed design

- Use the owner-approved public source license and keep package/release metadata
  consistent with it.
- Keep the npm package private because distribution is through GitHub source
  releases, not the npm registry.
- Add `quickstart` as the exact-lock install/build/start path and keep `start` as
  the already-built foreground lifecycle command. Foreground operation makes
  stopping cross-platform, visible, and free of stale PID-file failure modes.
- Add a small dependency-free Node release validator with pure, unit-tested
  version/file/database-path rules and a thin filesystem/Git adapter.
- Use separate GitHub Actions workflows for CI, dependency review, CodeQL, and
  tag release. The release workflow reruns the authoritative gate rather than
  trusting a prior branch run.
- Use a human-reviewed release branch/PR to update version and changelog. After
  merge, an owner creates the matching annotated tag; automation verifies and
  publishes the GitHub Release.

## Data and migration impact

There is no schema change. Existing databases remain compatible. The application
data path stays outside the checkout and `ON_TRACK_DATA_DIR` remains available
for tests and advanced use. The release check examines tracked filenames only;
it never opens or prints user database content.

## Phases

1. **Release contract RED.** Add failing unit tests for version/tag matching,
   required public files, and forbidden tracked database paths.
2. **Release contract GREEN.** Implement the validator, add v0.0.1 metadata and
   scripts, then prove the focused tests and local release check.
3. **Public-source surface.** Add the license, changelog, contributor/security/release docs,
   product-focused README content, and durable project/architecture updates.
4. **Automation.** Add least-privilege pinned GitHub workflows, Dependabot, issue
   templates, and a pull-request checklist.
5. **Security review.** Inspect command construction, GitHub token permissions,
   third-party action pinning, untrusted tag/input handling, secret exposure, and
   data-file exclusions.
6. **Independent review and verification.** Run the reviewer, address findings,
   execute the verification loop and a fresh-copy quick-start smoke test, inspect
   status/diff, and stop before commit.

## Test plan

- Unit: valid and invalid SemVer/tag pairs, manifest mismatch, missing public
  files, forbidden tracked SQLite/database paths, and benign similarly named
  source/docs paths.
- Integration: execute `npm run release:check` in the repository and with a
  simulated `v0.0.1` tag.
- Fresh source smoke: use a disposable copy without `node_modules` or build output,
  run the documented quick-start command against a disposable data directory,
  request the health endpoint, stop the foreground process, and confirm the
  database exists only in that data directory.
- CI syntax: parse all workflow YAML, inspect permissions/action pins, and run the
  same local commands referenced by automation.
- Full regression: `npm run verify`, including coverage and Playwright.

## Risks and mitigations

- **A source release is mistaken for a native installer:** state Node.js 24 as a
  prerequisite and describe v0.0.1 as alpha; native packaging remains explicit
  future work.
- **A tag publishes the wrong code/version:** release validation requires exact
  tag/package/lockfile agreement and the full suite passes before publishing.
- **Compromised CI dependency:** pin actions to immutable SHAs, minimize token
  permissions, use dependency review/Dependabot/CodeQL, and avoid arbitrary
  downloaded release scripts.
- **Private data enters Git:** ignore broad database families and fail release
  validation if a matching file is tracked. The default data directory remains
  outside the checkout.
- **Platform-native install breaks:** exercise installation and tests on Linux,
  macOS, and Windows before version tags are accepted.
- **GitHub settings remain permissive:** document branch protection, required
  checks, secret scanning, private-vulnerability reporting, and immutable release
  settings for the owner to enable after the repository exists.

## Open decisions

The original MIT default and later PolyForm decision were superseded before first
publication by [ADR-0005](../adr/0005-apache-2-license.md). A native installer
would materially change packaging and is deferred beyond the source-based
v0.0.1 alpha.

## Completion evidence

### TDD evidence

- RED: `npm test -- scripts/release-contract.test.ts` initially failed because
  the release validator did not exist. GREEN: version/tag/file/data-path cases
  passed after the dependency-free validator was implemented.
- Reviewer RED: invalid numeric prereleases (`1.0.0-01` and `1.0.0-alpha.01`),
  `.db3`/`.s3db`, lockfile-root mismatch, and absent changelog-version cases were
  reproduced by failing tests. GREEN: all 13 release-contract tests pass with
  standards-correct SemVer and expanded metadata/data-file validation.
- E2E RED: mobile WebKit exposed focus restoration from the closed creation
  dialog after the first animation frame. GREEN: focus is applied on the
  following frame; the repaired mobile journey and full two-browser suite pass.

### Security and review evidence

- Workflow YAML parses successfully. All 11 third-party action references are
  pinned to full official commit SHAs.
- Normal CI is `contents: read`. Only the final release job, after verification,
  receives `contents: write`.
- The release workflow fetches full history and refuses a tag whose commit is not
  an ancestor of `origin/main`; remote setup requires a restricted `v*.*.*` tag
  ruleset.
- Database ignore checks cover `.sqlite`, `.sqlite3`, `.db`, `.db3`, `.s3db`,
  journals/WAL/shared memory/backups, and On Track export/backup paths. The
  validator examines Git filenames only.
- The independent reviewer initially reported two Medium findings (tag provenance
  and prerelease SemVer validation). Both were fixed and regression-tested; final
  review reports no High or Medium findings.

### Verification report

- Fresh quick start: PASS — `npm run quickstart` installed 497 locked packages,
  built, started on loopback, returned HTTP 200 from `/api/health`, stopped with
  `Ctrl+C`, and created `0600` SQLite/WAL files only in the explicit disposable
  external data directory.
- Release contract: PASS — local and `RELEASE_TAG=v0.0.1` checks; mismatched tag
  exits nonzero.
- Aggregate: PASS — final `npm run verify` completed build, typecheck, lint,
  format, coverage, migration integration, desktop Chromium/mobile WebKit E2E,
  and production audit.
- Tests: PASS — 61 tests in 8 files, plus 8 focused migration tests and 2 isolated
  restart E2E journeys.
- Coverage: PASS — statements 85.71%, branches 80.55%, functions 82.79%, lines
  88.53%.
- Security: PASS — production and full dependency audits report zero
  vulnerabilities.
- Git: no database or generated artifact appears in the release candidate; no
  commit, tag, push, setting change, or GitHub Release was created.

Overall: READY to be committed and published as the source-based v0.0.1 alpha
after the owner creates the GitHub repository and enables the documented branch,
tag, security, and immutable-release settings. Cross-platform CI configuration is
prepared but cannot run until the source is pushed to GitHub.
